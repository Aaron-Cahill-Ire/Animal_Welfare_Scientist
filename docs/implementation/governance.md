## Repository trust

Every external executable starts Unreviewed. Reviewed requires an identified reviewer, immutable release, dependency inventory, maintainer verification, isolated execution, permission inventory and dated scope. Code/dependency/permission/ownership changes reset this label. Revoked packages retain their visible failure record and cannot be offered as executable trials. No external repository code runs automatically on catalogue inclusion.

## Data handling

Only public or synthetic inputs are supported. Local CLI execution stays local; the browser trial runs supplied safe example data in a worker. Runtime assets are downloaded from a pinned Pyodide CDN; no input is uploaded to a model provider. Do not place credentials or restricted information in source records, input files, traces, exceptions or published examples. Classification is user-supplied and is not an automatic privacy detector. No telemetry, accounts or server-side storage are implemented. Local run files are the user's responsibility; remove them when no longer needed. Public benchmark generation uses only allowlisted development cases. Sensitive/protected evaluations are not supported by the public harness.

Before any pilot, appoint a data owner and custodian, document consent and processing authority, minimise/pseudonymise inputs, agree retention and deletion, review publication and re-identification risk, and provide a correction/withdrawal route. No personal or farm-specific metadata is published by default. Incident process: stop affected execution, revoke the version, preserve access-limited incident evidence, contact the owner through a private channel, remove exposed information and rotate affected credentials/cases.

## Protected evaluation

Public development cases are not protected evaluation. A future custodian must keep hidden cases outside developer-accessible repositories, audit access, rotate leaked cases, and verify processor terms before any external model processing. No current prototype may claim protected-case performance or independent verification.

## Human decisions

Shortlisting, protocol approval, ethical approval, preregistration submission, physical studies, bench testing and purchasing remain human responsibilities. Workflow checkpoints record explicit decisions/results and their provenance; a JSON approval record is an attestation, not authentication or regulatory permission. The system never executes an experiment, buys a component or submits a registration.

## Evaluation and maturity

Starter cases are synthetic, purposive and developer-authored. Semantic assertions compare the agent with its documented simple baseline using the same input and rubric. Report counts, failures, abstentions and timing, not statistical efficacy or population accuracy. A passing starter suite permits at most Prototype. Configurations are content-addressed; changed source/schema/runtime cannot inherit evaluation. Independent verification needs external welfare and methods reviewers, an appropriately powered frozen protocol and published decisions.

## Partner evaluation still required

Recruit 5–8 welfare researchers with explicit outreach permission. Observe their current workflow, define a matched baseline and count setup, correction and review time. Predeclare the primary endpoint, useful improvement threshold, critical failure ceiling and sample-size rationale before a confirmatory trial. Keep negative results visible. Do not claim time savings, welfare benefits or research usefulness from these starter checks.
